===== 5. Cache state, measured rather than assumed (the epic's standing lesson)
# A "before" number is a cache state, not a fact. Consecutive touches, same statement:
#
#   unbounded, 1 char : 929 ms (fully cold, after other probes evicted it)
#                        94 ms (first touch)
#                        41.4 / 42.6 / 41.0 / 42.1 ms (warm, stable)
#   org-scoped, 1 char:  0.28 / 0.23 / 0.31 ms  — stable from the first touch, because the
#                        whole working set is 26 pages and never leaves shared_buffers
#
# What reproduces exactly is the PLAN, which is the part worth writing down.

====================================================================================
SUMMARY

  shape                    rows scanned   plan                                  cold -> warm
  ---------------------------------------------------------------------------------------
  org-scoped, 1 char       1 000          Bitmap Index Scan customer_org_idx    0.23 - 0.65 ms
                                          -> filter  (26 buffers, all           (no cold/warm
                                          shared hit)                            distinction)
  org-scoped, 2/3/4 char   1 000          same                                  0.13 - 1.30 ms
  unbounded, 1 char        200 000        Seq Scan                              929 -> 41 ms
  unbounded, 3 char        200 000        Seq Scan                              ~42 ms warm

DECISION: no minimum q length.

The endpoint only ever runs the org-scoped shape, and that is 0.23-0.65 ms at 1 character
with no cache sensitivity at all. The unbounded row is here ONLY to give the slope: cost is
linear in the TENANT's own size, so a 20 000-customer tenant projects to ~4 ms warm and
~90 ms on a cold cache. The cold end is the honest one to design against, and even that
does not justify a character floor.

Not copied from slice 3's 2, and not from its lesson's 3 — measured. Slice 3's 1706 ms
pathology (pg_trgm's GIN index chosen for a <3-char LIKE, then rechecked over the whole
table) is structurally unreachable here: see section 3 — with enable_bitmapscan forced off
the planner STILL picks the org index, never customer_name_search_trgm_idx. The org filter
is the access path, so a character count would defend nothing it does not already bound.

NO INDEX ADDED and none declined: V62's customer_name_search_trgm_idx and V75's
customer (email) were already present and neither is used by this shape. The planner was
never asked for a new one, so there is no refusal to record.
