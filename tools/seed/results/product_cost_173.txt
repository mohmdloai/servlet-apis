# WHAT WAS MEASURED. perfdb's products are ALL uncosted (146 164 products, 0 costed — the seeder
# predates V92 and the story keeps it that way), so the FILTERed cost sums would have nothing to
# sum. The capture therefore runs inside ONE transaction that costs the chosen org's 728 products
# at 60 % of base_price and freezes that onto its order lines, runs the EXPLAINs, and ROLLS BACK
# (§5 confirms 0 costed products / 0 costed lines afterwards). The plan shape does not depend on
# the values; the timings do reflect the arithmetic actually running over real rows.
#
# The org is the one with the most order lines (de431e06…, 8 510 lines over all time; 5 082 in
# the last 366 days; 612 tracked products). Every org on perfdb is within a few rows of it.
#
# FINDINGS
#  1. top-products: BEFORE (quantity + revenue) and AFTER (+ four cost aggregates) are the SAME
#     plan — Index Scan sales_order_org_status_idx → Nested Loop lines → Nested Loop product →
#     Sort → GroupAggregate → top-N heapsort — at the same estimated cost (7129.68 vs 7131.55) and
#     the same 38 166 shared-hit buffers. Warm: 39.3 ms vs 39.4 ms. The four FILTER sums are
#     free at this scale; the cold first run (65 vs 71 ms) is the buffer read, not the query.
#  2. by=profit changes only the top-N sort key (the aggregate expression, DESC NULLS LAST):
#     57 ms on its first (cold-ish) run, same plan and buffers as by=revenue.
#  3. GET /reports/profit (the total: same join, no product join, no GROUP BY): 23.7 / 22.6 ms
#     over 366 days, 3.7 ms over the default 30-day window. Plain Aggregate over the same
#     Nested Loop; 18 039 buffers.
#  4. inventory-valuation: BEFORE and AFTER are the same plan (Bitmap Index Scan inventory_pk →
#     Nested Loop product_pkey → Aggregate, 3 595 buffers, estimate 5762 vs 5770). The 573 ms on
#     3a is the COLD first touch of this org's inventory/product pages (perfdb's tables outsize
#     shared_buffers, so the first read of anything is disk); the two AFTER runs are 5.5 / 4.0 ms
#     warm. Read 3a as "cold", not as "the old query was slower".
#  5. NO INDEX ADDED. Nothing here scans a table; every read already rides sales_order_org_status_idx,
#     sales_order_line_order_idx, inventory_pk and product_pkey, and the new columns are read off
#     rows those indexes already fetch. V73's rule: an index the planner would not choose is write
#     cost for no read benefit — and there is no predicate on unit_cost / cost_price to index.
